# SRE 与 SLI / SLO / SLA

## SRE 是什么

"用软件工程方法运营系统可靠性"。核心转变：可靠性是**功能需求**，有明确目标、
有预算、有数据，而不是"越稳越好"的玄学。

## SLI / SLO / SLA

| 概念 | 是什么 | 例子 |
|---|---|---|
| SLI | 可靠性**指标**（测量值） | HTTP 成功率、P99 延迟 |
| SLO | 指标的**目标** | 30 天成功率 ≥ 99.9% |
| SLA | 对**外承诺**+违约条款 | 商业合同 99.5%（比 SLO 松） |

SLO 从用户旅程推导：不是监控什么就定什么，而是"用户能正常用的标准是什么"。

## Error Budget（错误预算）

```
预算 = 1 - SLO    （99.9% → 0.1% = 30 天 43 分钟不可用额度）
```

- 预算充足 → 放心发布新版本
- 预算耗尽 → 冻结功能发布，全力修可靠性（这是**纪律**，不是建议）
- 预算让"稳定性 vs 迭代速度"的争论变成数据决策

## 起步实践（小环境版）

1. 挑 2-3 个核心服务，各定 1 个可用性 SLO + 1 个延迟 SLO
2. Prometheus 记录规则算 SLI，Grafana 展示预算消耗（docs/04-可观测性）
3. 每月 review：预算烧在哪 → 输入 docs/03-事件复盘 与容量决策
