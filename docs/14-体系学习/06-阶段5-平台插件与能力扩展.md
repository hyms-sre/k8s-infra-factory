# 阶段 5 — 平台插件与能力扩展

## 前置条件

- 阶段 3 检查点通过（集群已引导）
- cn 环境需先完成阶段 4（否则镜像拉不动）

## 学习目标

1. 为什么节点一直 `NotReady`，装完 Cilium 就好了？
2. `ClusterIP` / `NodePort` / `LoadBalancer` 的区别，MetalLB 补上了哪一环？
3. 为什么用 Gateway API 而不是 Ingress？
4. Longhorn 提供了什么，它和 NFS 的区别在哪？
5. 插件的**安装顺序**为什么不能随便调？

## 核心概念

### 1. 安装顺序不是随意的

```
① CNI (Cilium)          ← 必须最先: 没有它节点永远 NotReady
      ↓
② CoreDNS 转 Running     ← 依赖 CNI
      ↓
③ Metrics Server         ← 提供资源指标
      ↓
④ MetalLB                ← 给 LoadBalancer 分配 IP
      ↓
⑤ Gateway API + Envoy GW ← 依赖 MetalLB 提供入口 IP
      ↓
⑥ Longhorn               ← 提供持久卷
      ↓
⑦ Headlamp               ← 面板, 最后装
```

**为什么 CNI 必须最先**：kubelet 需要 CNI 才能给 Pod 配网络；
CNI 没装时 CoreDNS 会卡在 `Pending`，很多后续组件也跟着起不来。

**为什么 Gateway 在 MetalLB 之后**：`Gateway` 需要一个 `LoadBalancer` 类型的
Service 来暴露，而 `LoadBalancer` 的 IP 由 MetalLB 分配。

### 2. 三种 Service 类型

| 类型 | 作用范围 | 谁提供 |
|---|---|---|
| `ClusterIP` | 集群内 | Kubernetes 自带 |
| `NodePort` | 通过节点端口暴露 | Kubernetes 自带 |
| `LoadBalancer` | 一个独立 IP | **云厂商 / MetalLB** |

裸金属环境没有云厂商，`LoadBalancer` 会一直 `Pending` —— **MetalLB 就是补这一环**，
从预置 IP 池里分配地址。

### 3. Gateway API vs Ingress

| | Ingress | Gateway API |
|---|---|---|
| 抽象层级 | 单资源 | Gateway（入口）+ HTTPRoute（路由）分离 |
| 角色划分 | 弱 | 基础设施方管 Gateway，业务方管 Route |
| 能力 | 基础 | 支持更细的流量策略、多协议 |

本项目用 **Gateway API（Envoy Gateway 实现）**，把"入口"和"路由"拆开，职责更清晰。

### 4. Longhorn 提供什么

Longhorn 是 **CSI 分布式块存储**：

- 给 `PersistentVolumeClaim` 提供卷
- 支持副本、快照、备份
- 与 NFS 的区别：Longhorn 是块存储 + 副本复制；NFS 是共享文件系统

> 本项目的 lab 环境用 Longhorn 给 Harbor 等有状态服务提供持久卷。

## 动手实验

### 实验 1：观察"没有 CNI"的状态

在装 CNI **之前**：

```bash
kubectl get nodes          # NotReady
kubectl get pods -A        # CoreDNS Pending
kubectl get pods -n kube-system -o wide
```

记下现象。**这就是为什么要先装 CNI。**

### 实验 2：装 CNI，看节点转 Ready

按 `k8s-plugins/networking/` 里的说明安装 Cilium，然后：

```bash
kubectl get nodes -w        # 观察 NotReady → Ready
kubectl get pods -A         # CoreDNS 转 Running
```

### 实验 3：给集群一个入口 IP

1. 安装 MetalLB，配置地址池
2. 装 Gateway API CRD + Envoy Gateway
3. 建 `Gateway` + `HTTPRoute` 指向一个测试 Service

```bash
kubectl get gateway         # 应拿到 EXTERNAL-IP
curl http://<LB_IP>:<port>  # 应能访问到后端
```

### 实验 4：验证持久存储

```bash
# 创建一个 PVC
kubectl apply -f <一个PVC yaml>
kubectl get pvc             # 应为 Bound
```

### 实验 5：打开面板

按 `k8s-plugins/platform/headlamp/` 部署，通过入口 IP 访问 Headlamp，
能看到节点、Pod、工作负载。

## 检查点

- [ ] 所有节点 `Ready`
- [ ] CoreDNS 等系统组件全部 `Running`
- [ ] 能说出为什么 CNI 必须最先装
- [ ] 有一个 `LoadBalancer` 拿到了外部 IP
- [ ] `HTTPRoute` 能正确转发到后端
- [ ] PVC 能 `Bound`
- [ ] Headlamp 面板可访问

## 常见坑

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| 先装 Gateway 后装 MetalLB | Gateway 一直没 IP | 顺序反了，先 MetalLB |
| CNI 没装就调其他 | 一堆 Pod Pending | 先装 CNI |
| MetalLB 地址池与网段冲突 | IP 拿不到或不可达 | 地址池要选**未被占用**的网段 |
| Pod CIDR 与节点网段重叠 | 路由混乱 | 规划时避开 |
| Longhorn 副本数超过节点数 | 卷一直 `Degraded` | 副本数 ≤ 可用节点数 |
| 镜像拉不到导致装不上 | Pod `ImagePullBackOff` | 回阶段 4 检查镜像链路 |
