# 阶段 1 — 环境与 IaC 基础

## 前置条件

- 能 SSH 登录一台 Linux 机器（部署机）
- Python ≥ 3.9、Terraform ≥ 1.5 已安装
- 能访问 vSphere/vCenter（**没有也没关系**，本阶段可以用 `terraform plan` 只读体验）

## 学习目标

学完本阶段你应该能回答：

1. 为什么这个项目用 Terraform 而不是 Shell 脚本？
2. `cluster.yaml` 改了之后，哪些文件会变、哪些不会？
3. `terraform plan` 输出的 `+ create` / `~ update` / `- destroy` 分别在说什么？
4. 为什么"销毁重建"在这个项目里是**正常操作**而不是事故？

## 核心概念

### 1. 声明式 vs 命令式

| | 命令式（Shell） | 声明式（Terraform） |
|---|---|---|
| 你写什么 | "先建 VM，再装包，再……" | "我要 3 台 4C8G 的 VM" |
| 重复执行 | 可能重复创建 / 报错 | 自动算出差异，幂等 |
| 环境漂移 | 无从感知 | `plan` 能看出来 |
| 重建 | 靠脚本重跑，状态未知 | `destroy` + `apply`，结果确定 |

### 2. 本项目的三层结构

```
cluster.yaml          ← 唯一配置入口（你要改的就是它）
      │  generate.py  ← 生成器：YAML → HCL
      ▼
vm.tf (for_each)      ← 生成的资源定义（不要手改）
      │  terraform apply
      ▼
vSphere VM × N
      │  Cloud-Init
      ▼
kubeadm-ready 节点
```

**关键**：`vm.tf` 是**生成物**。改配置要改 `cluster.yaml` 后重新 generate，而不是直接改 `vm.tf`。

### 3. State（状态文件）

Terraform 用 `terraform.tfstate` 记录"我建了什么"。
`plan` 就是拿 **配置文件** 和 **state** 对比，算出要做什么。

> ⚠️ State 里含敏感信息（IP、凭据），本项目已将其排除出版本控制。

### 4. `for_each` 而非 `count`

本项目用 `for_each` 遍历节点 map。区别：

- `count`：按索引定位（`vm[0]`），**删中间一台会导致后面全部重建**
- `for_each`：按 key 定位（`vm["worker-01"]`），**增删单台互不影响**

这是"能安全地加/删节点"的基础。

## 对应仓库文件

| 文件 | 作用 | 该不该手改 |
|---|---|---|
| `terraform/vsphere/cluster.yaml` | **唯一配置入口**：集群名、节点、网络、K8s 版本、工具 | ✅ 改这里 |
| `terraform/vsphere/generate.py` | 生成器：`cluster.yaml` → `vm.tf` | ❌ 除非扩展功能 |
| `terraform/vsphere/vm.tf` | 生成的 VM 资源 | ❌ 生成物 |
| `terraform/vsphere/main.tf` / `locals.tf` / `variables.tf` / `outputs.tf` | 资源、局部值、变量、输出 | ⚠️ 谨慎 |
| `terraform/vsphere/provider.tf` | vSphere provider 与版本约束 | ⚠️ 谨慎 |
| `terraform/vsphere/data.tf` | 查询已有资源（数据中心/主机/网络/模板） | ⚠️ 谨慎 |
| `terraform/vsphere/README.md` | 本模块说明 | ✅ 参考 |

## 动手实验

### 实验 1：读懂配置入口

```bash
cd terraform/vsphere
cat cluster.yaml          # 观察顶层键: cluster / masters / workers / network / kubernetes / os / ssh / tools / harbor
```

回答：把 `workers` 从 3 改成 5，预期会新增几台 VM？

### 实验 2：生成并对比

```bash
python generate.py        # 生成 vm.tf
git diff vm.tf            # 看生成物怎么变（若已纳入版本控制）
```

> 建议改前先备份 `vm.tf`，改回来后对比，建立"配置 → 生成物"的直觉。

### 实验 3：只读计划

```bash
terraform init
terraform plan             # 只读，不会真的建 VM
```

观察输出里的 `+ create`，数一数是不是和 `cluster.yaml` 里的节点数一致。

### 实验 4（重要）：破坏性验证

故意把某个节点的 IP 改错一位，再 `plan`，观察：

- 是 `~ update` 还是 `- destroy` + `+ create`？
- 为什么改 IP 会触发重建？

改回来。**这一步比顺利跑通更有价值。**

## 检查点

全部通过才能进入阶段 2：

- [ ] 能说清 `cluster.yaml → generate.py → vm.tf → terraform apply` 的数据流
- [ ] 知道 `vm.tf` 是生成物，不该手改
- [ ] `terraform plan` 能跑出结果（无语法错误）
- [ ] 能解释 `for_each` 比 `count` 好在哪
- [ ] 能说出改 IP / 改规格 / 加节点分别会发生什么

## 常见坑

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| 直接改 `vm.tf` | 下次 generate 后被覆盖 | 改 `cluster.yaml`，重新 generate |
| 忘了 `terraform init` | 报 provider 缺失 | 先 `init` |
| 版本不一致 | provider 版本冲突 | 看 `provider.tf` 的版本约束 + lock 文件 |
| 以为 `plan` 会改东西 | — | `plan` 只读；`apply` 才动手 |
| 删中间一台节点 | 后续节点全部重建 | 这是 `count` 的行为；本项目用 `for_each` 规避 |
