# 阶段 4 — CN 网络环境与镜像仓库

> **直连公网的环境可以跳过本阶段**，直接进入 [阶段 5](06-阶段5-平台插件与能力扩展.md)。
> 但如果你在国内网络下部署，这一阶段是**必过项**。

## 前置条件

- 阶段 3 检查点通过
- 理解"集群建起来了但拉不到镜像"是网络问题，不是集群问题

## 学习目标

1. 为什么国内环境需要 OpenWrt + Harbor 两层，而不是简单配个镜像加速？
2. DNS 在整条链路里扮演什么角色？为什么它错了后面全错？
3. Harbor 的 **Proxy Cache** 是怎么做到"第一次回源、之后走本地"的？
4. 节点上的 `certs.d` 是干什么的？为什么它配错了会导致超时？

## 核心概念

### 1. 问题拆解

国内部署 Kubernetes 会遇到两类问题，**必须分开解决**：

| 问题 | 表现 | 解决层 |
|---|---|---|
| **DNS 污染** | 域名解析到错误 IP | OpenWrt（dnsmasq + 代理出口） |
| **镜像拉不动** | `dial tcp ... i/o timeout` | Harbor（Proxy Cache） |

只做其中一个都不够：DNS 通了但镜像还是慢；镜像缓存了但上游域名解析不对也回源不了。

### 2. 三层结构

```
K8s 节点 ──DNS──▶ OpenWrt (.210) ──代理出口──▶ 上游
   │                dnsmasq 本地域解析
   │
   └──拉镜像──▶ Harbor ──Proxy Cache──▶ 上游 registry
                (第一次回源, 之后本地命中)
```

### 3. Harbor Proxy Cache 的工作方式

Harbor 建一个 **proxy 项目**（如 `dockerhub`），绑定一个上游 registry。
节点拉 `docker.io/library/nginx` 时：

1. 请求打到 Harbor 的 `/v2/dockerhub/library/nginx/...`
2. Harbor 第一次**回源**上游拉取，**并落盘缓存**
3. 第二次同样请求**直接命中本地缓存**，不再出网

> 判断有没有真缓存：看 Harbor 存储目录大小是否增长。
> **只拉 manifest 不会增长，要拉完整镜像。**

### 4. 节点侧：`certs.d` 与 `config_path`

节点 containerd 靠 `/etc/containerd/certs.d/<registry>/hosts.toml` 决定"这个 registry 走哪"：

```toml
[host."https://harbor.example.com/v2/dockerhub"]
  capabilities = ["pull", "resolve"]
  override_path = true
```

**两个最容易踩的坑**：

1. **项目名必须和 Harbor 真实项目名一致** —— 不一致会 404，然后 containerd **回退直连上游** → 超时。
2. **containerd 的 registry `config_path` 必须是单一路径**（如 `/etc/containerd/certs.d`）。
   写成冒号分隔的多路径，CRI 会**静默忽略整个目录** → 拉镜像直连上游 → 超时。

> 第 2 条是"看起来配了却不生效"的经典原因。排查方法：
> `journalctl -u containerd | grep host=` 看它到底在连哪个 registry。

## 动手实验

### 实验 1：先验证"不配会怎样"

在阶段 3 的集群上直接拉一个镜像：

```bash
crictl pull docker.io/library/busybox:1.36
```

观察超时现象。记下错误里的 IP —— 那通常是**DNS 被污染**的结果。

### 实验 2：部署 OpenWrt 并验证 DNS

```bash
cd examples/openwrt
cp terraform.tfvars.example terraform.tfvars   # 填参数
terraform init && terraform apply
```

验证：

```bash
nslookup harbor.<你的域> <OpenWrt_IP>
```

### 实验 3：部署 Harbor 并验证缓存

```bash
cd examples/harbor
cp terraform.tfvars.example terraform.tfvars
terraform init && terraform apply
```

拉一个镜像两次，**对比耗时**，并观察 Harbor 存储增长：

```bash
# 第一次（回源，慢）
crictl pull docker.io/library/hello-world:latest
# 第二次（命中缓存，快）
```

### 实验 4（关键）：确认走的是 Harbor

```bash
# 看 containerd 到底连了哪个 registry
journalctl -u containerd --since "3 minutes ago" | grep -E "host=|fetch failed"
```

期望：**没有** `host=registry-1.docker.io` 的失败记录。

## 检查点

- [ ] 能说出 DNS 污染和镜像拉不动是**两个**独立问题
- [ ] OpenWrt 能正确解析本地域
- [ ] Harbor 的 proxy 项目与上游绑定正确
- [ ] 第二次拉同一镜像明显更快，且 Harbor 存储增长
- [ ] `journalctl` 里没有直连上游的失败记录
- [ ] 能说出 `config_path` 多路径为什么会导致"配了不生效"

## 常见坑

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| DNS 被污染 | 解析到莫名其妙的 IP | 走 OpenWrt，不要用公网 DNS |
| certs.d 项目名写错 | 404 后回退直连 → 超时 | 核对 Harbor 真实项目名 |
| `config_path` 多路径 | 配了 certs.d 但完全不生效 | 改成单一路径 |
| 只拉 manifest | Harbor 存储不增长 | 要拉完整镜像才会落盘 |
| 上游本身不通 | 回源失败 | 检查 Harbor 到上游的连通性 |
| 节点没配 DNS | 解析不了 Harbor 域名 | 检查节点 `/etc/hosts` 或 DNS |
